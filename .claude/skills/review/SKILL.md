# $ARGUMENTS 리뷰

단계를 말하지 않았으면 마일스톤 `README.md` 단계 표에서 `진행 중`인 단계로 정한다. "Mn 마무리"면 맨 아래 절을 따른다.

## 1. 직접 돌려 보기
1. 명세의 확인 명령을 돌린다: `cargo test -q -p 패키지`, 공식 채점기, `cargo clippy -q -p 패키지`, `cargo fmt --check -p 패키지`. 포맷이 어긋나도 고치지 않고 알리기만 한다.
2. 측정이 있는 단계면 `--release`로 직접 재고 환경을 적는다. 학습자의 예측과 같은 조건으로 잰다.
3. 골격 커밋과의 차이로 학습자가 쓴 부분을 본다: `git log --oneline -- <패키지 경로>`, `git diff <골격 커밋> -- <패키지 경로>`.
4. 테스트가 놓칠 만한 입력을 몇 개 더 넣어 본다(패닉, 경계값). 명세 밖의 CLI 경계값은 보지 않는다.

## 2. 기록 (`LOG.md`의 그 단계 절)
5. **결과와 피드백**: 실제 값(환경 포함)과 학습자의 예측을 나란히 놓는다. 맞았으면 왜 맞았는지, 틀렸으면 추론의 어느 고리에서 틀렸는지(개념 문서의 어느 절)를 쓴다. 예측이 비어 있으면 결과만 쓰고 비어 있다고 적는다.
6. **배운 것**: `QA.md`의 그 단계 항목과 이번 대화에서 중요한 지식을 3~6줄로 다시 짚는다. 잡은 버그는 `버그: 증상 → 원인 → 교훈`으로 쓴다.
7. **힌트 단계**: 이 단계에서 준 가장 높은 단계(`QA.md`의 힌트 줄).
8. 재미와 막힌 시간이 비어 있으면 학습자에게 채워 달라고 한 줄로 부탁한다.

## 3. 이해도 질문
9. 3~5개를 번호를 매겨 한꺼번에 낸다. 개념(그 절의 핵심)과 코드(왜 이렇게 동작하나, 입력이 바뀌면 어떻게 되나)를 섞는다. 답은 보여 주지 않는다.
10. 학습자가 답하면 ○△✕로 채점하고 보충한다. 틀린 개념은 다음 브리핑이 반영하도록 `REVIEW.md`에 남긴다.

## 4. 설계·구조 조언 (채팅, 이 순서로)
11. 잘한 설계 1~3개를 구체적으로.
12. 설계·구조: 모듈 경계, 소유권과 빌림, 오류 흐름, `unsafe` 건전성(`// SAFETY:`가 1순위). `docs/RULES.md`의 설계 원칙 번호로 짚는다. 고칠 방향은 말로 하고, 필요하면 3~10줄짜리 다른 예로 보인다. 학습자의 코드를 다시 써 주지 않는다.
13. 정확성: 테스트와 채점기가 잡은 문제를 재현 명령과 함께.
14. 이름과 스타일은 지적하지 않는다.

## 5. 남길 것
15. `REVIEW.md`에 틀대로 덧붙인다: 날짜와 커밋, 확인한 것, 이해도 질문과 점수(채점한 뒤), 설계·구조, 정확성, 다음 할 일.
16. 마일스톤 `README.md` 단계 표의 상태를 `완료` 또는 `미완(사유)`로 바꾸고, 커밋 메시지를 제안한다(예: `M1-2: 리뷰 반영 - 축출 순서`).
17. 학습자의 코드는 고치지 않는다.

## 마일스톤 마무리 ("Mn 마무리")
- 마지막 단계의 리뷰가 끝났는지 확인한다. 안 끝났으면 그 단계 리뷰부터 한다.
- 단계를 가로지르는 이해도 질문 5개를 낸다(예: 캐시의 세트와 TLB의 공통 구조).
- 체크포인트(CURRICULUM "체크포인트"): `LOG.md`의 숫자, `REVIEW.md`의 점수, `git log --date=short --pretty='%ad %s'`로 세 추세를 판단하고, 다음 마일스톤의 기간과 골격 양 조정을 제안한다. 근거가 약하면 약하다고 말한다.
- 그 장의 요약 절(6.7 등)에 해당하는 한 쪽 정리를 `REVIEW.md` 끝에 쓴다.
- 루트 `README.md`의 상태를 `완료`로 바꾸고, 원하면 "Mn 논문"으로 논문 세션을 열 수 있다고 알린다.
