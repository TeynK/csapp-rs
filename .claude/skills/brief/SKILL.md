# $ARGUMENTS 시작

마일스톤만 받았으면(`M1`) 그 마일스톤 `README.md` 단계 표의 첫 미완료 단계로 정한다. 마일스톤 폴더가 없으면 첫 단계(`M1-1`)다.

## 1. 준비
1. `docs/CURRICULUM.md`에서 그 마일스톤과 단계 항목(CSAPP 절, 할 일, 확인, Rust)과 "골격 단계", "예측 규칙", "개념 문서 기준"을 읽는다.
2. 앞 단계의 `LOG.md`(예측 적중, 막힌 시간, 힌트), `REVIEW.md`(틀린 이해도 질문, 남은 설계 조언), `QA.md`를 읽는다. 틀린 개념은 이번 개념 문서나 예측에 반영한다.
3. `docs/GLOSSARY.md`를 읽는다.
4. 이 단계에 필요한 도구와 이 머신의 값을 확인한다. 쓰는 도구(valgrind, perf, gdb 등)가 있는지 보고, 측정하는 단계면 `lscpu`, `uname -r`, 캐시 구성(`lscpu -C`)을 본다. 없는 도구는 설치 명령을 명세의 "준비"에 적는다. 설치는 학습자가 한다.

## 2. 마일스톤의 첫 단계일 때
5. `milestones/mN-주제/`를 만들고 `.claude/skills/brief/templates/`의 틀로 `README.md`, `LOG.md`, `QA.md`, `REVIEW.md`를 만든다.
6. 루트 `README.md` 표에서 그 마일스톤 이름을 폴더 링크로 바꾸고 상태를 `진행 중`으로 한다.
7. 랩이 있는 마일스톤이면 핸드아웃이 `labs/`에 있는지 보고, 없으면 받는 명령을 README "준비"에 적는다. 핸드아웃에 무엇이 들었는지(채점기, 트레이스, 참조 바이너리) 직접 확인한다.
8. `docs/GLOSSARY.md`의 그 마일스톤 표를 채운다(CSAPP 용어, 기호, 식별자).

## 3. 개념 문서 `concepts/chNN-k-주제.md`
9. `.claude/skills/brief/templates/concept.md`의 순서를 따른다. 기준:
   - 그 단계의 CSAPP 절을 하나도 빼지 않는다. 문서 끝 체크리스트에 절 번호마다 문서의 어느 곳에서 다뤘는지 적는다. 절 목록은 CURRICULUM의 "CSAPP 절 커버리지"를 따른다.
   - 설명, 그림, 문제는 자작한다. 책의 문장, 그림, 연습문제 원문, 해설을 옮기지 않는다(공개 저장소).
   - 절마다 자작 문제 1~3개와 단계별 풀이를 넣고, 풀이는 `<details>`로 접는다. 풀이의 숫자는 `/tmp`에서 코드로 검산한다.
   - 책 연습문제: 그 절을 책에서 펼치면 나오는 연습문제를 풀라고 안내하고, 해답이 책 각 장 끝에 있다고 적는다. 문제 번호는 확인한 출처(학습자가 책에서 확인해 준 목록)가 있을 때만 적는다. 튜터는 책을 볼 수 없다.
   - 예측 실마리: 이 단계 예측에 쓰는 모델과 식, 이 머신의 값(확인한 명령과 함께), 어느 경계에서 무엇이 바뀌는지 같은 추론의 방향. 답은 쓰지 않는다.
   - 이 머신의 수치는 확인한 것만 쓰고 출처 명령을 적는다.
   - 쓰지 않는 것: 예측의 답, 그 단계의 `todo!()`를 그대로 푸는 코드.

## 4. 골격 코드
10. CURRICULUM의 골격 단계에 맞춰 쓴다.
    - 패키지는 `cargo new --lib crates/이름` 또는 `cargo new apps/이름`으로 만든다(멤버가 자동으로 추가된다). 외부 크레이트는 루트 `[workspace.dependencies]`에 적는다.
    - 이름은 `docs/GLOSSARY.md`에서 가져온다. 새 이름은 사전에 먼저 적는다.
    - 학습 대상 함수는 시그니처, 문서 주석(하는 일, 불변식, 경계 조건), `todo!()`만 둔다. 몸체를 짐작하게 하는 주석은 쓰지 않는다.
    - CLI, 입출력, 출력 형식, 테스트 틀은 완성해서 준다. CLI는 clap(derive)으로 쓴다.
    - 테스트: 모듈 안의 단위 테스트와 `tests/`의 통합 테스트. 경계값을 넣고, 테스트 이름은 무엇을 보는지 드러나게 짓는다.
    - 튜터가 방금 쓴 골격 파일에만 `rustfmt --edition 2024 <파일>`을 쓸 수 있다. `cargo fmt`는 쓰지 않는다.
11. 골격을 확인한다: `cargo build -q -p 패키지` 통과, `cargo clippy -q -p 패키지`의 경고 확인, `cargo test -q -p 패키지`가 `todo!()` 때문에만 실패하는지(실패한 테스트 수를 센다).
12. 골격에 처음 나오는 Rust 문법 2~4개를 골라 둔다(채팅의 "골격 읽기").

## 5. 참조 구현으로 검증 (학습자에게 보여 주지 않는다)
13. 서브에이전트(Agent 도구)에게 맡긴다. 넘길 것: 골격 경로, 명세 초안, 확인 명령, 작업 폴더 `/tmp/csapp-ref/mN-k/`. 시킬 것:
    - 저장소를 그 폴더로 복사해 `todo!()`를 채운다. 코드는 파일 도구로만 쓴다(Bash heredoc 금지). 이 폴더의 편집은 `.claude/settings.json`이 허용한다.
    - 테스트, 공식 채점기, 측정을 실제로 돌린다.
    - 돌려줄 것: 통과 여부, 실제 출력, 골격·테스트·명세에서 고칠 점(너무 약하거나 지나친 테스트, 시그니처의 문제). 코드는 돌려주지 않는다.
    - 끝나면 `/tmp/csapp-ref/mN-k/`를 지운다.
14. 고칠 점을 골격과 명세에 반영하고, 다 맞을 때까지 13을 반복한다.
15. 서브에이전트의 결과를 학습자에게 옮길 때 예측의 답이 될 값은 거른다.

## 6. 명세 (마일스톤 `README.md`의 그 단계 절)
16. 틀의 단계 절을 채운다: 목표(무엇을 왜, 뒤에서 어디에 쓰이나), 읽을 것(개념 문서 경로와 읽는 시간), 채울 함수(파일, 함수, 한 줄 설명), 확인 명령과 완료 기준, 예측 질문, 범위 밖과 확장.
17. 예측 질문 1~2개는 CURRICULUM의 "예측 규칙"을 지킨다. 개념 문서와 이 머신의 값만으로 추론할 수 있어야 하고, 새 용어는 질문 바로 앞에서 C·어셈블리 말로 풀어 준다. 감이 없을 만한 수치는 범위 보기로 낸다. 답은 쓰지 않는다.
18. 단계 표의 상태를 `진행 중`으로 하고, `LOG.md`에 그 단계 절을 틀대로 덧붙인다(예측 칸은 비워 둔다).

## 7. 채팅
짧게 보낸다.
- 준비한 것: 개념 문서, 골격(패키지와 채울 함수 수), 명세의 경로
- 골격 읽기: 처음 나온 Rust 문법 2~4개를 C와 비교해 한 줄씩
- 예측 질문(용어 풀이와 함께)
- 첫 할 일: `git add -A && git commit -m "Mn-k: 골격"` → 개념 문서 읽기 → `LOG.md`에 예측 → 구현

## 하지 않는 것
- 학습 대상 함수의 몸체나 그것을 그대로 푸는 예시 코드 쓰기(개념 문서와 채팅 포함)
- 예측의 답을 어디에든 쓰기
- 학습자가 쓴 코드 고치기
