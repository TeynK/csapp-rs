# 논문 가치 (답안지)

질문까지만 먼저 보고 논문을 읽으세요. 5줄 노트(문제 · 핵심 아이디어 · 기대는 Dn 개념 · 비교 대상 · 한계)를 쓴 뒤에 아래 가치와 비교하면, 내 노트와 다른 점이 가장 큰 배움이 됩니다.

## 먼저: 품고 읽을 질문

논문을 열기 전에 자기 나름의 답을 한 줄 적어 두면, 읽으면서 무엇을 찾아야 하는지가 분명해집니다.

- **P1** SSD에 4KB 페이지 하나를 덮어쓰면 플래시에는 실제로 얼마나 쓰일까? 그 차이는 어디서 생길까?
- **P2** "FIFO는 단순하지만 미스율이 나쁘다"는 평가는 어떤 가정 위에 있었을까?
- **P3** LRU는 히트 때마다 무슨 일을 해야 하고, 그게 멀티코어에서 왜 비쌀까?
- **P4** 연산량을 줄이지 않았는데 어떻게 빨라졌을까?
- **P5** "비밀 값을 주소로 쓰지 않는다"는 규칙을 지켰는데도 왜 비밀이 샐까?
- **P6** 압축 라이브러리가 어떻게 sshd의 함수를 바꿔치기할 수 있었을까?
- **P7** SSD는 수백만 IOPS를 내는데, DB는 왜 그 일부밖에 못 쓸까?
- **P8** fork+exec가 "우아한 설계"라는 통념의 근거와 숨은 비용은 무엇일까?
- **P9** 타이머 시그널로 스레드를 선점하면 어디서 비용이 생길까?
- **P10** huge page로 TLB reach를 늘리면 어떤 대가를 치를까?
- **P11** OS가 페이지를 알아서 올리고 내리는 것이 DB에게는 왜 독이 될 수 있을까?
- **P12** LLM의 KV 캐시 낭비는 9장의 어떤 단편화와 같은 문제일까?
- **P13** 페이징을 응용이 직접 구현하는 것과 OS의 가상 메모리에 맡기는 것은 각각 무엇을 잃을까?
- **P14** mmap의 문제(P11)를 피하면서 가상 메모리의 장점만 쓸 수는 없을까?
- **P15** unsafe 코드에서 "규칙을 어겼다"는 건 정확히 누구와의 약속을 어긴 걸까?
- **P16** 구글 규모에서 1% 개선이 왜 논문이 될 만큼 큰일일까?
- **P17** epoll을 io\_uring으로 바꾸기만 하면 왜 거의 빨라지지 않을까?
- **P18** Rust 컴파일러를 통과한 코드에는 어떤 버그가 남을까?
- **P19** C 커널 API 위에 안전한 Rust 래퍼를 씌우면 무엇을 얻고 무엇을 치를까?
- **P20** unsafe를 "적게 쓰는 것"과 "작은 곳에 가두는 것"은 무엇이 다를까?

## 그다음: 논문의 가치 (노트를 쓴 뒤에 읽기)

### P1 · How to Write to SSDs — VLDB 2026

DB가 "얼마나" 쓰느냐만큼 "어떻게" 쓰느냐가 SSD의 성능과 수명을 좌우한다는 걸 보여 줍니다. 제자리에 덮어쓰는 기존 방식을 위치를 옮겨 쓰는(out-of-place) 설계로 바꾸자, YCSB-A에서 처리량은 1.65\~2.24배 늘고 트랜잭션당 플래시 쓰기는 6.2\~9.8배 줄었습니다. 저장장치 내부 구조를 알아야 소프트웨어 설계가 바뀐다는 사례입니다.

### P2 · FIFO Queues are All You Need for Cache Eviction — SOSP 2023

"FIFO는 단순하지만 미스율이 나쁘다"는 오래된 평가를 14개 데이터셋, 6,594개 실제 트레이스로 뒤집었습니다. 핵심은 대부분의 객체가 짧은 시간에 한 번만 쓰인다는 관찰이고, 작은 FIFO 큐로 이들을 빨리 걸러 내는 것만으로 더 낮은 미스율과 16스레드에서 LRU의 6배 처리량을 냈습니다. 복잡한 알고리즘보다 정확한 관찰 하나가 이긴다는 연구 방식 자체가 배울 점입니다.

### P3 · SIEVE is Simpler than LRU — NSDI 2024

LRU보다 단순한데 더 효율적인 교체 알고리즘을 제시했고, 실제 캐시 라이브러리 5곳에 평균 20줄 미만의 수정으로 적용했습니다. 히트 때 리스트를 옮기지 않아 락이 필요 없고, 그 덕분에 16스레드에서 최적화된 LRU의 두 배 처리량을 냅니다. 단순함이 멀티코어 확장성으로 이어진다는 점에서 6장과 12장을 함께 잇는 논문입니다.

### P4 · FlashAttention — NeurIPS 2022

어텐션 최적화의 관점을 "연산량"에서 "메모리 계층 사이의 데이터 이동"으로 바꿨습니다. 근사 없이 정확한 결과를 내면서도 타일링으로 느린 HBM 접근을 줄여 더 빠르고 긴 문맥을 가능하게 했고, 이후 FlashAttention-2·3으로 이어졌습니다. 6장의 메모리 계층 관점이 AI의 핵심 성능 문제를 푼 대표 사례입니다.

### P5 · GoFetch — USENIX Security 2024

암호 구현의 표준 방어인 "상수 시간 프로그래밍"(비밀을 주소로 쓰지 않기)이 하드웨어 최적화 하나로 무너질 수 있음을 보였습니다. Apple M 시리즈의 데이터 의존 프리페처는 캐시에 있는 포인터처럼 생긴 값을 따라가 읽어 오는데, 이를 이용해 OpenSSL·Go 같은 실제 구현에서 키를 빼냈습니다. 성능을 위한 캐시 기능이 보안 계약을 깨뜨릴 수 있다는 교훈입니다.

### P6 · xz 백도어 공격 경로 분석 — arXiv 2024 (프리프린트)

2024년 xz 백도어 사건을 단계별 공격 경로로 정리하고, 단계마다 어떤 방어가 통했을지 따진 분석입니다. 동적 로더가 프로그램 시작 때 실행하는 IFUNC 해석 함수가 공격의 진입점이 됐다는 점에서, 링킹이 곧 보안 문제라는 걸 보여 줍니다. 기존 분석들을 모아 정리한 동료 심사 전 자료이므로, 원 공개 글과 대조하며 읽으세요.

### P7 · What Modern NVMe Storage Can Do, And How To Exploit It — VLDB 2023

NVMe SSD 여러 개를 단 서버 한 대가 초당 1,000만 회 이상의 I/O를 낼 수 있는데, 기존 DB는 그 일부밖에 못 쓴다는 격차를 측정으로 보여 줬습니다. 이어 I/O 경로를 다시 설계하면 데이터가 메모리의 10배인 상황에서도 초당 100만 건이 넘는 TPC-C 트랜잭션이 가능함을 입증했습니다. "이제 병목은 하드웨어가 아니라 소프트웨어"라는 최근 흐름을 대표합니다.

### P8 · A fork() in the road — HotOS 2019 (워크숍)

모두가 배우는 fork가 1970년대 기계에 맞춘 영리한 임시방편이었고, 지금은 OS 구현에 짐이 된다고 주장합니다. 실험으로 증명하는 논문이 아니라 주장을 펼치는 글이지만, 교과서의 "당연한 설계"를 의심하는 연습으로 가치가 큽니다. 직접 만든 spawn과 비교하며 동의할 부분과 반박할 부분을 나눠 보세요.

### P9 · The Benefits and Limitations of User Interrupts for Preemptive Userspace Scheduling — NSDI 2025

인텔의 사용자 수준 인터럽트라는 새 하드웨어 기능을, 장점뿐 아니라 한계까지 측정한 균형 잡힌 평가입니다. 선점이 아주 잦은 경우를 빼면 기존 선점 메커니즘과 같거나 더 나은 성능을 더 일정한 오버헤드로 내지만, 다른 소프트웨어 계층이 정책을 제약하면 이득이 작다는 결론입니다. 새 기술을 과장 없이 평가하는 법의 좋은 본보기입니다.

### P10 · Mosaic Pages: Big TLB Reach with Small Pages — ASPLOS 2023

huge page 같은 기존 방법은 물리 메모리 연속성에 기대고, 그 연속성을 만드는 조각 모음 비용이 이득을 상쇄할 수 있다는 문제를 짚었습니다. 해싱으로 매핑을 제한해 여러 변환을 TLB 엔트리 하나에 압축함으로써, 연속성 없이도 시뮬레이션에서 TLB 미스를 워크로드에 따라 6\~81% 줄였습니다. 이론(해싱)과 하드웨어 설계가 만나는 지점을 볼 수 있습니다.

### P11 · Are You Sure You Want to Use MMAP in Your DBMS? — CIDR 2022

여러 DB가 mmap으로 시작했다가 큰 비용을 치르고 직접 버퍼 관리로 돌아선 경험을 정리해, mmap이 정확성과 성능 양쪽에서 함정인 이유를 실험과 함께 경고합니다. 핵심은 페이지를 언제 올리고 내릴지를 OS가 정해 버리면 DB가 통제할 수 없는 일이 생긴다는 점입니다. 공개 반박도 함께 찾아 읽으면, 같은 사실을 두고 결론이 갈리는 시스템 연구의 실제 모습을 볼 수 있습니다.

### P12 · Efficient Memory Management for LLM Serving with PagedAttention — SOSP 2023

LLM 서빙에서 요청마다 커졌다 줄었다 하는 KV 캐시가 단편화와 중복으로 메모리를 낭비해 배치 크기를 묶어 둔다는 문제를, OS의 가상 메모리와 페이징 아이디어로 풀었습니다. 낭비를 거의 없애고 요청 사이의 공유까지 가능하게 해 처리량을 2\~4배 높였고, 이후 LLM 서빙의 사실상 표준이 됐습니다. 고전 OS 개념이 최신 AI 인프라의 병목을 푼 가장 선명한 사례입니다.

### P13 · vAttention — ASPLOS 2025

P12가 페이징을 응용 수준에서 다시 구현하면서 KV 캐시를 가상 주소상으로도 쪼개 놓는 바람에, 어텐션 커널을 고쳐 써야 하는 비용이 생겼다고 지적합니다. 대신 가상 주소는 연속으로 예약하고 물리 메모리만 요구 시 붙이는 방식으로, 기존 커널을 그대로 쓰면서 토큰 생성을 vLLM보다 최대 1.97배 빠르게 했습니다. "추상화를 어느 계층에 둘 것인가"라는 시스템 설계의 오래된 질문이 AI에서 다시 불붙은 논쟁입니다.

### P14 · Virtual-Memory Assisted Buffer Management — SIGMOD 2023

P11의 결론("DB는 mmap을 피하라")과 전통적인 버퍼 풀 사이의 중간 길을 제시합니다. 가상 메모리 하드웨어는 주소 변환에 활용하되, 언제 읽고 내보낼지는 DB가 직접 통제하는 방식입니다. 두 논문을 나란히 읽으면 "OS 기능을 쓸 것인가, 피할 것인가"가 이분법이 아님을 알게 됩니다.

### P15 · Tree Borrows — PLDI 2025

unsafe Rust에서 무엇이 정의되지 않은 동작(UB)인지 정하는 별칭 규칙의 새 모델입니다. 이전 모델(Stacked Borrows)이 실제로 흔한 unsafe 패턴까지 막던 문제를 고쳐, 많이 쓰는 크레이트 3만 개에서 거부하는 테스트를 54% 줄이면서도 컴파일러 최적화의 근거는 증명으로 지켰습니다. 아직 Rust의 공식 별칭 규칙이 정해지지 않은 상황에서 유력한 후보이므로, 매일 쓰는 `// SAFETY:` 주석이 무엇을 보장해야 하는지 가장 구체적으로 알려 줍니다.

### P16 · Characterizing a Memory Allocator at Warehouse Scale — ASPLOS 2024

구글 전체 데이터센터에서 TCMalloc을 처음 종합 분석해, 할당 크기·수명·패턴이 워크로드마다 크게 다르다는 걸 데이터로 보였습니다. 이를 바탕으로 할당기 캐시 계층마다 개선을 넣어 전체 서버군에서 처리량 1.4% 향상, 메모리 3.4% 절감을 얻었습니다. 이 규모에서는 1%가 막대한 비용이라는 점에서, 할당기가 여전히 살아 있는 연구 주제인 이유를 보여 줍니다.

### P17 · High-Performance DBMSs with io\_uring: When and How to Use It — VLDB 2026

io\_uring을 기존 인터페이스 자리에 그냥 끼워 넣으면 이득이 6\~10%에 그치지만, 배칭과 비동기 실행에 맞춰 구조를 바꾸면 두 배 넘게 빨라진다는 것을 보였습니다. 지연·사이클 모델로 성능을 미리 계산하고 측정과 맞춰 보는 방식이 돋보이며, 이 지침을 PostgreSQL에 적용해 실제 개선까지 확인했습니다. "인터페이스를 바꾸려면 구조를 바꿔야 한다"는 교훈이 핵심입니다.

### P18 · Understanding and Detecting Real-World Safety Issues in Rust — IEEE TSE 2024

실제 Rust 프로젝트의 메모리 안전 버그 70건, 동시성 버그 100건, 패닉 110건을 직접 분석해 Rust가 무엇을 막고 무엇을 못 막는지 실증했습니다. 수명(lifetime)을 잘못 이해한 것이 많은 메모리 버그의 원인이었고, 분석을 바탕으로 만든 검사기가 알려지지 않았던 버그 96개를 찾았습니다. "컴파일되면 안전하다"는 착각을 바로잡아 주는 논문입니다.

### P19 · An Empirical Study of Rust-for-Linux — USENIX ATC 2024

리눅스 커널에 Rust를 들이는 과정을 드라이버·커밋·메일링 리스트 데이터로 처음 실증 분석했습니다. Rust가 커널 취약점을 줄이지만 모두 없애지는 못하고, 안전 보장을 잘못 다루면 런타임 오버헤드와 개발 비용을 크게 치른다는 균형 잡힌 결론을 냈습니다. 과대평가도 과소평가도 아닌, 증거로 기술을 평가하는 법을 보여 주며 최우수 논문상을 받았습니다.

### P20 · Asterinas — USENIX ATC 2025

Rust로 만든 기존 OS들조차 unsafe를 제대로 가두지 못했다는 문제를 짚고, unsafe를 작은 기반 프레임워크 안에만 가두는 "프레임커널" 구조를 제안했습니다. 210개가 넘는 리눅스 시스템 콜을 지원하며 리눅스와 비슷한 성능을 내면서도, 메모리 안전을 위해 믿어야 하는 코드(TCB)를 전체의 약 14%로 줄였습니다. 9주 동안 sysx에서 연습한 "안전한 API 뒤에 unsafe를 가두기"가 OS 규모에서도 통한다는 증거입니다.
